# RAG 候选证据缺失原因分析与实验方案

## 一、结论先行

当前出现“15 个候选里只有一两个正确证据”甚至“完全没有正确证据”，**不是单一组件造成的**。

按当前 50 个待审块、750 个候选证据和现有代码进行分析后，建议按以下优先级处理：

1. **先修正评估口径和黄金集定义**  
   当前很多“缺失正确证据”并不是真正的检索失败。尤其是合规块，通常不存在一条能够直接证明“全文合规”的规则证据。
2. **将一个待审 chunk 拆成多个原子审查主张用于检索**  
   保持待审 chunk 文件不变，但不要继续使用整个长 chunk 作为唯一检索 query。
3. **扩大候选召回池，再进行真正的相关性重排**  
   当前 15 条候选不是统一重排后的 Top15，存在正确证据在 BM25 Top17，却因为候选池提前凑满 15 条而被丢弃的情况。
4. **补充知识库覆盖并增加适用性元数据**  
   当前知识库只有 4 部规程，部分具体作业要求根本不在库中。换 embedding、换向量库、重排都无法召回不存在的规则。
5. **再优化知识库 chunk，并比较 embedding 与 reranker**  
   知识库确实存在过短标题块和过长规则块，但这不是当前最大问题。
6. **分库召回最后做，并优先采用逻辑路由而不是物理分库**  
   分库主要解决规则适用范围、版本、专业领域和候选配额问题，不能代替补库和查询改写。

因此，当前不建议直接开始比较 Chroma、Milvus、Qdrant。对于目前只有 1,077 个知识库 chunk 的规模，向量库产品通常不是召回质量差异的主要来源。

## 二、当前流程实际在做什么

### 2.1 当前生产检索

`hybrid_rag_review_v8.py` 当前配置：

- Embedding：`text-embedding-v3`
- 向量库：Chroma，余弦距离
- 稀疏检索：BM25
- 混合方式：Dense 与 BM25 的加权 RRF
- `TOP_K = 5`
- `SIMILARITY_THRESHOLD = 0.1`
- 当前没有 cross-encoder 或 LLM reranker

当前所谓“混合重排”只是 RRF 融合。RRF 根据 Dense、BM25 各自排名计算融合分数，不会逐条理解“待审主张和规则证据是否真正相关”。

### 2.2 当前黄金标注候选生成

每个待审块使用**完整 chunk 内容**作为 query：

1. Dense 取 Top20。
2. BM25 取 Top20。
3. Dense Top20 与 BM25 Top20 通过 RRF 得到 Hybrid Top20。
4. 先依次加入 Dense Top5、BM25 Top5、Hybrid Top5。
5. 去重后不足 15 条，才从三路第 6 名开始继续补。
6. 一旦获得 15 个唯一候选，立即停止。

这里有两个关键问题：

- 最终候选的 `rank` 是“加入候选池的先后顺序”，不是统一相关性排序。
- 三路中排名较后的正确证据可能还未加入，候选池就已经凑满 15 条并停止。

所以，“15 条里正确证据很少”既可能是召回失败，也可能只是候选构造和排序方式有问题。

| 项目 | 数量 |
|---|---:|
| 待审块 | 50 |
| 每块候选 | 15 |

| 最终标签 | 待审块数 | 至少有一条有用证据 | 缺失证据 | 平均有用证据数 |

这说明：

- 真正需要找违规依据的 11 个不合规块中，已有 10 个召回了正确证据。
- “缺失正确证据”主要集中在合规、不确定和不适合评估样本。
- 当前的 22 个缺失不能直接解释为“检索 Recall 很差”。

### 3.2 三种检索方式都有独立价值

52 次有用证据命中中：

| 检索方式 | 包含的有用证据数 |
|---|---:|
| Hybrid | 43 |
| Dense | 35 |
| BM25 | 34 |

仅被单一路径找到的有用证据：

| 独占来源 | 数量 |
|---|---:|
| 仅 Dense | 6 |
| 仅 BM25 | 3 |
| 仅 Hybrid | 3 |

因此：

- 不能只保留向量检索。
- 不能只保留 BM25。
- Hybrid 能提高覆盖，但也无法代替扩大召回池和真正 rerank。

### 3.3 当前 15 条候选排序不够好

在 28 个至少包含一条有用证据的样本中，以当前候选最终顺序统计：

| 指标 | 结果 |
|---|---:|
| Recall@1 | 9 / 28 |
| Recall@3 | 18 / 28 |
| Recall@5 | 21 / 28 |
| Recall@10 | 27 / 28 |
| Recall@15 | 28 / 28 |

说明候选池中经常已经有正确证据，但没有排在前面。若线上只使用 Top5，仍会漏掉一部分已被召回的正确证据。

## 四、为什么会缺失正确证据

## 4.1 第一类：评估口径造成的“假缺失”

这是当前数量最大的表面原因。

### 合规块没有唯一的“正确证据”

对于不合规块，可以标注一条直接冲突的规则作为正确证据。

但对于合规块，“没有发现冲突”通常是对多个规则进行检查后的结论，而不是由某一条规则直接证明。若强制每个合规块都必须在 15 条内出现一条“正确证据”，会人为放大缺失数量。

### 不适合普通规则检索的样本

部分块属于：

- OCR 或单位错误；
- 语义角色不明确；
- 示例、红线清单、目录等特殊内容；
- 旧 v5 样本映射到 v9 后，原问题已不在当前块中。

这些样本应该进入独立任务，而不是计入普通规则召回失败。

### 应如何修改

将评估任务拆成四类：

1. **违规证据召回**：是否召回能够证明冲突的规则。
2. **合规支持召回**：是否召回与待审主张直接相关、可用于核验的规则，不要求一条规则证明整体合规。
3. **适用性/上下文判断**：是否因设备、区域、作业类型、专用或永久用途等条件不足而无法判断。
4. **不适合 RAG 审查**：OCR、错别字、目录、示例、红线清单等。

普通 Retrieval Recall 的分母中，应排除“不适合 RAG 审查”和映射漂移样本。

---

## 4.2 第二类：整块直接查询导致检索意图被稀释

当前待审块长度约为 286 到 2,269 字符，一个块中可能同时存在多个要求、阈值、设备和作业条件。

将整个块直接用于 Dense 和 BM25，会产生以下问题：

- BM25 被大量非核心词占据，真正的关键条款词权重下降。
- Dense embedding 需要用一个向量概括多个审查主张，语义中心变模糊。
- 一个块里不同条款可能分别对应不同规程，单次检索难以全部召回。
- 标题、说明、表格和具体要求混合后，模型不知道当前要核验哪个主张。

### 已验证的例子

#### 高处作业安全带

待审块包含“1.5m”相关要求。知识库中存在：

> `煤矿安全规程::chunk592`：2m 以上高处作业必须系安全带。

但是使用完整待审块查询时，该规则的 BM25 排名约为 511。  
这不是知识库缺失，也不是知识库规则切错，而是长 query 稀释和表达不一致造成的。

若查询改为：

> 高处作业达到多少米必须系安全带

召回难度会明显降低。

#### 上隅角恢复作业阈值

知识库有“工作面回风隅角”的甲烷传感器报警、断电和复电阈值表，但待审文档使用“上隅角”。

知识库中“上隅角”字面命中为 0，“回风隅角”规则存在。  
这属于术语归一化和 query rewrite 问题。

### 应如何修改

待审 chunk 继续固定，但额外生成检索用的原子主张：

```text
父待审块
├─ 主张1：高处作业达到 1.5m 必须系安全带
├─ 主张2：作业平台应设置防护栏
└─ 主张3：安全带挂点应牢固
```

每个主张分别检索，再将候选证据合并回父待审块。

建议为每个原子主张生成多种 query：

- 原始主张；
- 标题 + 当前条款；
- 术语归一化后的主张；
- 规则问句，例如“高处作业安全带高度要求”；
- 风险或违规表达，例如“未系安全带的禁止条件”。

这属于**检索 query 层改造**，并不要求重新切分待审文档。

## 4.3 第三类：候选池提前截断，且没有真正重排

### 已验证的例子：锚杆预紧力矩

知识库中存在直接证据：

> `GB/T...::chunk52`：锚杆预紧力矩不低于设计预紧力矩的 90% 为合格。

该证据在完整 BM25 检索中排名第 17，已经进入 BM25 Top20。

但当前候选池先加入 Dense Top5、BM25 Top5、Hybrid Top5，并在得到 15 个唯一候选后停止，因此 BM25 第 17 名没有进入最终标注候选。

这说明该案例不是 embedding 失败，也不是知识库缺失，而是候选池构造错误。

### 当前 RRF 不等于语义 reranker

RRF 只根据不同检索器中的排名融合：

```text
score = vector_weight / (rank_dense + 60)
      + bm25_weight / (rank_bm25 + 60)
```

它无法判断：

- 规则是同一设备还是相似设备；
- 规则是允许条件、禁止条件还是违规示例；
- 数值关系是更严格还是更宽松；
- 规则是否适用于当前矿井、区域和作业场景。

### 应如何修改

候选生成流程改成：

1. Dense Top50。
2. BM25 Top50。
3. 可选：稀疏向量或术语扩展检索 Top50。
4. 合并、去重，保留完整来源与原始排名。
5. 使用 bge-reranker 或 Qwen3-Reranker 对约 50 到 100 条候选统一打分。
6. 输出 rerank 后的 Top10 或 Top15。

用于人工标注时，不应仅展示最终 Top15，还应保留 Top100 的检索审计数据，以判断问题到底出在召回还是重排。

## 4.4 第四类：知识库覆盖不足

当前知识库只有 4 部文档，共 1,077 个 chunk：

- `GB/T 35056-2018 煤矿巷道锚杆支护技术规范`
- `防治煤与瓦斯突出细则`
- `山西省煤矿顶板安全管理规定`
- `煤矿安全规程`

部分待审块涉及更加具体的作业规程、内部标准、设备操作要求。若这些规则不在知识库中，任何 embedding、reranker 或向量库都无法召回。

### 已发现的疑似覆盖缺口

- “点动”相关具体操作要求：当前知识库中无直接命中。
- 瓦斯抽采管路回收时传感器布置的具体要求：当前知识库中疑似没有直接规则。

### 应如何修改

标注时增加一等标签：

```text
target_evidence_status:
  - found_in_kb
  - likely_not_in_kb
  - applicability_unclear
  - not_retrieval_task
```

对于 `likely_not_in_kb`：

1. 记录应补充的规则类型和来源。
2. 经过人工确认后补库。
3. 补库后重新执行召回评估。

不要把“知识库没有规则”误判成 embedding 模型质量差。

## 4.5 第五类：适用条件和语义角色不明确

部分规则表面相似，但适用条件不同。

例如“起吊锚杆”：

- 规则可能禁止使用永久支护锚杆、锚索进行起吊。
- 待审文本中的“起吊锚杆”也可能指专门设计的起吊锚杆。

即使检索到了相关规则，若待审块没有说明锚杆用途，也不能直接判违规。

类似问题包括：

- 永久支护 vs 临时或专用设施；
- 高瓦斯矿井 vs 普通矿井；
- 冲击地压危险区域等级；
- 工作面、回风流、上隅角等位置；
- 违规示例 vs 允许性操作要求。

### 应如何修改

在 chunk 和规则元数据中增加：

- `semantic_role`：要求、禁止、例外、违规示例、定义、说明等；
- `applicable_domain`：顶板、瓦斯、运输、机电等；
- `applicable_object`：设备、作业、区域；
- `applicable_conditions`：矿井类型、危险等级、用途等；
- `source`、`article`、`effective_date`、`version`。

检索后增加“适用性判断”步骤，不要仅凭文本相似度直接判定。

## 4.6 第六类：知识库 chunk 确实需要优化

知识库 chunk 统计：

| 指标 | 数值 |
|---|---:|
| 总数 | 1,077 |
| 平均字符数 | 195 |
| 中位数 | 129 |
| P90 | 378 |
| 最大值 | 3,686 |
| 小于 100 字符 | 401 |
| 大于 1,500 字符 | 8 |

候选中存在过短的纯标题块，例如：

- “第三节 钢丝绳和连接装置”
- “第十三章监控与通信 第一节一般规定”

这些块能命中关键词，但不能提供审查证据。

也存在超长规则块，一条有用规则被大量无关内容稀释。

### 但不建议统一缩小所有 chunk

现有 50 个待审块中，长度与有用证据数量没有简单的单调关系。长块不一定更差，短块也不一定更好。

正确做法是：

- 纯标题块与后续正文合并，不单独进入检索库。
- 超长规则按“条、款、列表项、表格行语义组”切分。
- 每个规则 chunk 保留父级章节、条号、标题上下文。
- 原始展示文本与检索文本分开存储。

建议字段：

```json
{
  "raw_content": "原始规则内容",
  "retrieval_content": "父标题 + 条号 + 当前规则 + 术语别名",
  "source": "煤矿安全规程",
  "article": "第五百九十九条",
  "semantic_role": "mandatory",
  "applicable_domain": ["高处作业"],
  "applicable_conditions": ["高度 >= 2m"]
}
```

## 4.7 Embedding 模型是不是主要问题

目前证据不足以认定 embedding 是主要问题。

原因：

- Dense 找到了 6 条 BM25 和 Hybrid 都未找到的独占有用证据，说明当前 embedding 有价值。
- BM25 也找到 3 条独占有用证据，说明词法检索不可替代。
- 多个漏召回案例可明确归因于整块 query、术语不一致、候选截断或知识库缺失。

BGE-M3 支持 dense、sparse 和 multi-vector 检索；Qwen3 提供专门的 Embedding 与 Reranker 模型。这些能力值得比较，但不能直接假设换模型就会解决当前问题。

正确比较方式：

- 固定相同知识库 chunk。
- 固定相同 query 策略。
- 固定完整目标证据标注。
- 每种模型取 Top100。
- 比较 Recall@5/10/20/50/100、MRR、nDCG。
- 然后再增加同一 reranker，比较 rerank 后指标。

如果不先修正 query 和黄金证据，模型比较结果会被其他问题污染。

参考：

- [BGE-M3 model card](https://huggingface.co/BAAI/bge-m3)
- [Qwen3 Embedding 官方说明](https://qwenlm.github.io/blog/qwen3-embedding/)

## 4.8 是否需要换 Milvus 或 Qdrant

可以实现并比较，但当前不应把它作为质量优化的第一步。

对于 1,077 个向量：

- Chroma、Milvus、Qdrant 都可以轻松检索。
- 若使用相同 embedding、相同距离度量，并确保精确检索或足够高的 ANN 参数，结果应非常接近。
- 更换向量库主要影响扩展性、过滤能力、部署、索引类型、多向量和混合检索工程能力。

Milvus 支持多向量混合检索和 RRF/Weighted reranking，但这些是工程能力；是否提升本项目效果仍需使用同一黄金集验证。

参考：

- [Milvus Hybrid Search](https://milvus.io/docs/hybridsearch.md)
- [Milvus Reranking](https://milvus.io/docs/reranking.md)

建议在当前流程稳定后，使用同一批 query 和相同向量，验证 Chroma 与 Milvus 的 TopK 结果一致性，而不是把向量库切换当作首要召回优化。

## 4.9 是否需要分库召回

### 物理分库不是首要方案

如果正确规则不存在，分库仍然召回不到。  
如果 query 被长 chunk 稀释，分库也不一定解决。  
如果候选池提前停止，分库甚至可能增加候选冲突。

### 推荐逻辑分域和配额召回

保留统一知识库，但利用元数据进行路由：

1. 识别待审主张所属领域，如瓦斯、顶板、机电、运输。
2. 全局检索一路。
3. 可能相关的专业规则库分别检索一路。
4. 每个来源保留一定候选配额，避免某一大文档占满结果。
5. 合并后由统一 reranker 排序。
6. 最终根据适用条件过滤或降权。

分库或分域的主要价值是：

- 保证专业规则不会被大库淹没；
- 控制法律、国家标准、地方规定、内部制度的优先级；
- 管理规则版本和适用范围；
- 提升可解释性。

它不是修复当前 Recall 的第一手段。

## 五、对 22 个“缺失正确证据”的重新解释

建议将其重新归类，而不是都记为检索失败。

### A. 评估口径、样本映射或任务类型问题

- 不适合普通规则检索：`v9_006_chunk003`、`v9_006_chunk026`、`v9_006_chunk030`、`v9_066_chunk141`
- v5 到 v9 映射后原问题不在当前块：`v9_006_chunk023`、`v9_006_chunk024`
- 多个普通合规作业块没有唯一直接证据：  
  `v9_004_chunk013`、`v9_004_chunk060`、`v9_004_chunk087`、`v9_004_chunk161`、`v9_006_chunk161`、`v9_066_chunk089`、`v9_066_chunk100`、`v9_066_chunk112`

### B. 适用条件或上下文不明确

## 六、下一步实验顺序

## 阶段 0：清理黄金集定义

目标：先保证评估指标回答的是正确问题。

需要修改：

1. 为每个样本增加 `evaluation_task_type`：
   - `violation_evidence_retrieval`
   - `compliance_support_retrieval`
   - `applicability_check`
   - `not_retrieval_suitable`
2. 增加 `target_evidence_status`：
   - `found_in_kb`
   - `likely_not_in_kb`
   - `applicability_unclear`
   - `not_retrieval_task`
3. 修复 v5 到 v9 映射漂移样本。
4. 不再要求所有合规块必须存在唯一“正确证据”。
5. 对每个适合评估的原子主张，标注知识库中**所有可接受证据**，而不只是当前 15 条中的证据。

完成标准：

- 能明确区分“库里没有”和“检索没找到”。
- 能明确区分“没有唯一证据”和“候选证据全部错误”。

## 阶段 1：测 Oracle Recall，定位召回层问题

目标：暂时不考虑最终 Top15 和重排，先确认各检索器能否在较大范围内找到目标。

每个原子主张分别执行：

- Dense Top100
- BM25 Top100
- Hybrid Top100

统计：

- Recall@5
- Recall@10
- Recall@20
- Recall@50
- Recall@100
- MRR
- 首个正确证据排名
- `not_in_kb` 数量

判断方式：

- Top100 都没有目标：优先检查知识库覆盖、query、embedding。
- Top100 有、Top20 无：召回模型或 query 排名能力不足。
- Top20 有、最终 Top15 无：候选池构造问题。
- 最终 Top15 有、Top5 无：需要 reranker。

## 阶段 2：比较 query 策略

保持待审文档 v9 chunk 固定，比较：

| 编号 | Query 策略 |
|---|---|
| Q0 | 当前完整待审 chunk |
| Q1 | 父标题 + 当前具体条款 |
| Q2 | 从 chunk 中提取的原子审查主张 |
| Q3 | 原子主张 + 术语归一化/同义词扩展 |
| Q4 | 将主张改写为“应查找的规则问题” |

预期：Q2 和 Q3 应优先改善高处作业、上隅角、数值阈值等案例。

## 阶段 3：修复候选池并增加 reranker

建议候选流程：

```text
每个原子主张
  -> Dense Top50
  -> BM25 Top50
  -> 合并去重
  -> RRF 仅作为初步融合
  -> 统一 reranker 对 Top50~100 打分
  -> 主张级 Top10
  -> 合并回父待审 chunk
  -> 去重并保留证据覆盖信息
```

比较 reranker：

- bge-reranker
- Qwen3-Reranker

注意：reranker 只能改善已进入候选池的证据排序，不能找回召回池之外的证据。

## 阶段 4：比较 embedding

在阶段 0 到 3 固定后，再比较：

- 当前 `text-embedding-v3`
- `BAAI/bge-m3`
- Qwen3-Embedding

每种 embedding 使用同样的：

- 知识库 chunk；
- 原子 query；
- TopK；
- 目标证据；
- reranker 或不使用 reranker的两组实验。

重点看 Recall@50/100，而不是只看最终审查准确率。

## 阶段 5：补库与知识库 chunk 优化

1. 根据 `likely_not_in_kb` 样本补充规则来源。
2. 合并纯标题 chunk。
3. 拆分过长规则 chunk。
4. 构造 `retrieval_content`，保留标题、条号和术语别名。
5. 增加语义角色、适用条件、版本等元数据。
6. 重新运行阶段 1 到 4。

## 阶段 6：逻辑分库/分域召回

在知识库来源足够后，比较：

- 全库直接召回；
- 全库召回 + metadata filter；
- 全库一路 + 专业分域多路召回 + 每路配额；
- 分域召回后统一 rerank。

不要首先比较物理数据库数量，而要比较是否提升目标证据 Recall 和适用性准确率。

## 八、最终判断

对当前问题的原因排序如下：

| 原因 | 当前影响判断 | 是否优先处理 |
|---|---|---|
| 黄金集和“缺失证据”定义不准确 | 很高 | 是，第一步 |
| 使用完整待审 chunk 作为唯一 query | 很高 | 是 |
| 候选池提前截断、没有统一 rerank | 高 | 是 |
| 知识库缺少具体作业规则 | 高 | 是 |
| 适用条件和语义角色缺失 | 高 | 是 |
| 知识库 chunk 过短/过长 | 中 | 是，但不是第一步 |
| 当前 embedding 不够好 | 尚未证明，可能为中 | 修复前述问题后比较 |
| 未使用 reranker | 中到高，主要影响排序 | 应增加 |
| 未分库召回 | 低到中 | 后期做逻辑分域 |
| Chroma 本身导致召回差 | 当前证据不支持 | 暂不优先 |

最值得马上验证的改动不是重新切待审文档，也不是换 Milvus，而是：

> **固定 v9 待审 chunk，提取原子审查主张；Dense 与 BM25 各召回 Top50~100；合并后用 reranker 统一重排；同时把“库里没有规则”和“合规块没有唯一证据”从检索失败中分离出来。**
